# Contributing to Metal Slug Clone

Thank you for your interest in contributing to the Metal Slug Clone project! This document provides guidelines and best practices for contributing to this open-source game project.

## How to Contribute

### Reporting Bugs

If you find a bug in the game, please follow these steps:

1. **Search existing issues** to avoid creating duplicates
2. **Create a new issue** with a clear title and description
3. **Include reproduction steps** to help developers understand the problem
4. **Add relevant information** such as:
   - Game version
   - Operating system
   - Hardware specifications
   - Screenshots or videos (if applicable)

### Suggesting Features

We welcome feature suggestions! Please:

1. **Search existing issues** to see if the feature is already requested
2. **Create a new issue** with a clear title and detailed description
3. **Explain the use case** for the feature
4. **Include implementation ideas** if you have them

### Submitting Pull Requests

When submitting a pull request, please:

1. **Ensure your code follows the project's coding standards**
2. **Include tests** for new functionality
3. **Update documentation** as needed
4. **Write clear commit messages** that explain what changes were made

## Development Workflow

### Setting Up Your Development Environment

1. **Clone the repository**
2. **Install required dependencies** (Java, LibGDX, Gradle)
3. **Import the project** into your IDE
4. **Run the game** to verify setup

### Branching Strategy

We use the **Git Flow** branching model:

- **main**: Production-ready code
- **develop**: Development branch
- **feature/***: For new features
- **hotfix/***: For urgent fixes

### Code Style Guidelines

1. **Java Code Style**:
   - Follow Oracle's Java Code Conventions
   - Use meaningful variable and method names
   - Maintain consistent indentation (4 spaces)
   - Add documentation comments for public APIs

2. **LibGDX Specifics**:
   - Follow LibGDX project structure conventions
   - Use proper resource management
   - Follow LibGDX performance guidelines

## Testing

### Running Tests

Before submitting a pull request:

1. **Run all unit tests** to ensure no existing functionality is broken
2. **Run integration tests** for affected components
3. **Test manually** the functionality you've implemented

### Test Coverage

We aim for comprehensive test coverage:
- Unit tests for core components
- Integration tests for system interactions
- Manual testing for gameplay

## Code Review Process

1. **Pull requests are reviewed by maintainers**
2. **Feedback is provided constructively**
3. **Changes are made based on review comments**
4. **Pull requests are merged after approval**

## Documentation Standards

### Code Documentation

1. **Public APIs** must have comprehensive Javadoc
2. **Complex logic** should include inline comments
3. **Architecture decisions** should be documented

### User Documentation

1. **Game instructions** should be clear and accessible
2. **Feature descriptions** should be detailed
3. **Troubleshooting guides** should be provided

## Community Guidelines

### Code of Conduct

Be respectful and inclusive in all interactions:
- Be constructive in feedback
- Respect different viewpoints and experiences
- Be professional in all communications

### Recognition

Contributors will be recognized in:
- **CONTRIBUTORS.md** file
- **Credits** in the game itself
- **Release notes** for major contributions

## Getting Help

### Contact

If you need help with contribution guidelines:

1. **Open an issue** to ask questions
2. **Join community discussions** (if available)
3. **Contact maintainers** directly

### Resources

1. **Documentation** in the repository
2. **Existing code** as reference
3. **Community forums** (if available)
